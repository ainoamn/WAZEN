# تقرير تطوير وترقية منصة وازن

التاريخ: 12 أغسطس 2026  
النطاق: مراجعة الكود المحلي `C:\dev\WAZEN` والنسخة المنشورة `https://wazen-roan.vercel.app`

## 1. الخلاصة التنفيذية

المشروع المحلي أصبح أساساً جيداً لمنتج تجاري: تسجيل ودخول واستعادة كلمة المرور، محافظ شخصية وجماعية، جمعيات ورحلات، مستندات وفواتير، عزل مستأجرين، صلاحيات، سجل تدقيق، تشفير، اختبارات وCI. لكنه لم يصل بعد إلى حالة تشغيل تجاري كاملة.

المشكلة العاجلة هي وجود فرق كبير بين الكود المحلي والنشر الحالي:

- النسخة المنشورة تفتح لوحة المستخدم ولوحة الإدارة بهوية تجريبية `demo@wazen.app` وصلاحية `super_admin` دون تسجيل دخول حقيقي.
- النسخة المنشورة تعرض خمسة مستخدمين وأرصدة وفواتير تجريبية.
- مسارا `/api/health` و`/api/auth` يعيدان 404 في النشر، رغم وجودهما في الكود المحلي.
- هذا يدل على أن Vercel يشغّل بناءً أقدم أو إعداد نشر مختلفاً عن النسخة المؤمّنة محلياً.

لذلك ترتيب التنفيذ الصحيح هو:

1. إيقاف وصول Demo العام وتوحيد GitHub/Vercel مع الكود الحالي.
2. أخذ نسخة احتياطية واختيار طريقة تصفير قابلة للاستعادة.
3. تهيئة قاعدة إنتاج نظيفة وتشغيل الهجرات.
4. إنشاء مدير حقيقي وتفعيل TOTP قبل فتح الإدارة.
5. تطوير لوحة الإدارة من لوحة متابعة أولية إلى مركز تشغيل تجاري كامل.
6. ربط الدفع والبريد والمراقبة والنسخ الاحتياطي، ثم اختبار قبول وإطلاق محدود.

## 2. الموجود فعلياً الآن

### النظام المالي والمستخدم

- محافظ شخصية ومنزلية وسفر وجمعيات ومجموعات.
- أعضاء وصلاحيات داخل المحفظة: مالك، مدير، أمين صندوق، عضو، مدقق، ومشاهد.
- مساهمات إلزامية وفوائض شخصية لا تختلط بالصندوق.
- ترتيب أدوار الجمعية يدوياً أو أبجدياً أو بالقرعة أو هرمياً.
- مصروفات الرحلة وتقسيمها وتسويات استرداد ما دفعه العضو.
- حركات مالية بوحدات العملة الصغرى، وقيد مزدوج للعمليات الجديدة.
- مستندات وإيصالات وكشوفات مرقمة ذرياً وقابلة للطباعة والتنزيل.

### المصادقة والحماية

- تسجيل، تأكيد بريد، دخول، استعادة وتغيير كلمة المرور.
- إلغاء الجلسات القديمة بعد تغيير أو استعادة كلمة المرور.
- CSRF مرتبط بالجلسة، TOTP، ومفاتيح API محدودة الصلاحية والنطاق.
- صلاحيات منصة وصلاحيات محافظ مطبقة من الخادم.
- تشفير أسرار بإصدارات مفاتيح وفصل أغراض ودعم تدوير.
- منع SSRF، حماية Webhook وidempotency، وتنقية سجل التدقيق.
- اختبارات Backend وFrontend وE2E وبناء إنتاجي ناجح.

### الإدارة الحالية

توجد صفحات:

- `/admin`: نظرة عامة ومؤشرات أولية وكوبونات وفريق الإدارة وسجل تدقيق مختصر.
- `/admin/users`: بحث وتصفية وإيقاف/تفعيل حساب العميل.
- `/admin/payments`: مدفوعات وحالات وتسويات واسترداد.
- `/admin/reports`: MRR وARR وARPU ومؤشرات الاشتراك والتحصيل.

كما توجد عمليات خلفية لتغيير دور المنصة وحالة المستخدم والدفع وإنشاء كوبون، لكن بعضها لا يملك واجهة إدارة مكتملة.

## 3. النواقص والمخاطر مرتبة حسب الأولوية

### P0 — قبل أي استخدام حقيقي

1. **إغلاق Demo في الإنتاج**  
   يجب أن تكون القيم التالية صفراً: `WAZEN_DEMO_MODE=0` و`WAZEN_USE_NODE_SQLITE=0` و`WAZEN_TRUST_OAI_HEADERS=0`.

2. **نشر الكود الحالي بدلاً من البناء القديم**  
   يجب أن يظهر `/api/health` ويعمل نظام `/api/auth`، وأن يعاد توجيه الزائر غير المسجل من `/dashboard` و`/admin` إلى تسجيل الدخول أو يعاد له 401/403.

3. **قاعدة إنتاج دائمة**  
   يلزم Turso/Neon مناسب للتقنية المعتمدة، مع نسخة احتياطية واستعادة زمنية. الكود الحالي مهيأ لـ Turso/libSQL.

4. **تصفير آمن لا حذف مباشر**  
   لا يجوز حذف بيانات القاعدة قبل نسخة احتياطية، تقرير أعداد، وتأكيد اسم البيئة. الأفضل إنشاء قاعدة إنتاج جديدة ثم إبقاء القديمة للرجوع المؤقت.

5. **مدير حقيقي محمي**  
   بريد موثّق، كلمة مرور قوية، TOTP إلزامي، وعدم السماح بحذف أو تخفيض صلاحية آخر `super_admin`.

6. **أسرار الإنتاج**  
   توليد keyring وWebhook/job secrets جديدة، وعدم نسخ قيم تجريبية أو وضعها في Git.

### P1 — لوحة الإدارة التجارية

1. **المستخدمون بالتفصيل**
   - ملف مستخدم يعرض المستأجرين والمحافظ والاستخدام والاشتراك والجلسات ومفاتيح API.
   - إلغاء جلسات محددة أو جميع الجلسات.
   - قفل مؤقت، تعليق، إغلاق، واستعادة الحساب مع سبب وإجراء تدقيق.
   - Pagination وفلترة من الخادم؛ التنفيذ الحالي يجلب القوائم كاملة ولن يتوسع جيداً.

2. **الشركات والمستأجرون**
   - صفحة `/admin/tenants` تعرض المالك والأعضاء والدولة والعملة والخطة والاستخدام.
   - الدخول إلى تفاصيل الشركة دون انتحال صامت للهوية.
   - إن أضيفت ميزة “عرض كمستخدم”، فيجب أن تكون مؤقتة، مقيدة، ظاهرة للمستخدم، ومسجلة بالكامل.

3. **فريق الإدارة والصلاحيات**
   - دعوات موظفي الإدارة بدلاً من تعديل أدوار عبر API فقط.
   - أدوار: `super_admin`، `admin`، `finance`، `support`، `security_auditor`، `content_manager`.
   - واجهة مصفوفة الصلاحيات، TOTP إلزامي، وآلية موافقة مزدوجة للإجراءات الحساسة.

4. **الباقات والاشتراكات**
   - CRUD للباقات، المزايا، الحدود، الأسعار والدول.
   - ترقية/تخفيض، تجربة مجانية، إلغاء في نهاية المدة، وفترة سماح.
   - سجل تغييرات الأسعار وعدم تعديل سعر فاتورة سابقة.

5. **الفواتير والمدفوعات**
   - تفاصيل الفاتورة، محاولات الدفع، Webhook timeline، التسوية والاسترداد الجزئي/الكامل.
   - ربط فعلي بمزود دفع Checkout مستضاف؛ الموجود حالياً أساس محاسبي وWebhook وليس دورة تحصيل كاملة.
   - منع تعديل الدفع يدوياً دون سبب ومرجع وموافقة عند المبالغ الكبيرة.

6. **الكوبونات**
   - تعديل وتعطيل وتحديد الباقات والدول والعملاء وفترات الصلاحية.
   - حد لكل عميل وتقارير إساءة الاستخدام.

7. **سجل التدقيق والأمان**
   - بحث بحسب الموظف والإجراء والكيان والتاريخ والنتيجة.
   - أحداث أمنية: محاولات الدخول، TOTP، تغيير دور، تصدير بيانات، تغيير بوابة دفع.
   - تنزيل سجل موقّع أو تصدير آمن مع سياسة احتفاظ.

8. **التشغيل والوظائف**
   - حالة البريد وعمليات retry، Webhook failures، مهام الصيانة، نسخة التطبيق والهجرات.
   - ربط Sentry أو منصة مراقبة، وتنبيهات عند 5xx أو فشل الدفع أو النسخ الاحتياطي.

9. **طلبات الخصوصية والدعم**
   - إدارة طلبات تصدير/حذف البيانات بمراحل وموافقة وسجل إثبات.
   - نظام تذاكر دعم أو ربط أداة خارجية.

### P2 — التوسع التجاري والدولي

- Checkout ودفع حقيقي ودورة تجديد تلقائي وفواتير ضريبية صحيحة.
- مزود بريد فعلي وقوالب عربية/إنجليزية واختبارات تسليم.
- Country Packs مكتملة قانونياً وضريبياً لكل دولة، لا مجرد عملة ونسبة افتراضية.
- ترجمة جميع أخطاء API والنصوص، وصيغ تاريخ وأرقام وعناوين وهواتف.
- إعدادات إشعارات وتنبيهات الاستحقاق والدفع والتسوية.
- مرفقات آمنة إن احتجنا فواتير أو إثباتات: فحص نوع/حجم/فيروس، تخزين خاص وروابط مؤقتة.
- Feature flags وإطلاق تدريجي ومقاييس استخدام وتحويل وإلغاء اشتراك.
- تطبيق جوال/PWA لاحقاً بعد استقرار الـ API والاشتراكات.

## 4. خطة تصفير البيانات

### الخيار الموصى به: قاعدة إنتاج جديدة

هذا الخيار أكثر أماناً وقابلية للرجوع من حذف صفوف القاعدة الحالية.

1. إيقاف الكتابة أو وضع الموقع في Maintenance.
2. أخذ Export/Backup للقاعدة الحالية وتسجيل وقت النسخة وchecksum.
3. إنشاء قاعدة Turso جديدة باسم واضح مثل `wazen-production-v1`.
4. تشغيل `npm run db:migrate` على القاعدة الجديدة.
5. التحقق من جميع الجداول والهجرات وقيود الدفع والأرصدة.
6. إدخال الباقات الأساسية فقط؛ لا تُزرع بيانات مستخدمين أو أموال أو كوبونات تجريبية.
7. تهيئة المدير الحقيقي بالطريقة الموضحة أدناه.
8. ربط Preview/Staging أولاً، وتشغيل الاختبارات والدخول والفواتير وWebhook.
9. تغيير متغيرات Production في Vercel إلى القاعدة الجديدة وإعادة النشر.
10. إبقاء القاعدة القديمة Read-only لمدة متفق عليها، ثم حذفها فقط بقرار مستقل.

### خيار بديل: تصفير نفس القاعدة

ينفّذ فقط عبر سكربت مخصص، لا عبر أوامر SQL يدوية. السكربت المطلوب يجب أن يملك:

- `--dry-run` افتراضياً ويعرض عدد الصفوف في كل جدول.
- رفض العمل ما لم يكن `WAZEN_RESET_CONFIRM` مطابقاً لعبارة تشمل اسم البيئة والتاريخ.
- التحقق من وجود نسخة احتياطية حديثة.
- معاملة واحدة أو batch ذرية، وسجل نتيجة لا يحتوي أسراراً.
- الحفاظ على جدول `_wazen_migrations`، وإمكانية الحفاظ على `plans` فقط.

ترتيب الحذف التقريبي بسبب العلاقات:

1. `financial_operation_claims`, `webhook_events`, `rate_limits`, `email_outbox`.
2. `idempotency_keys`, `api_keys`, `totp_credentials`, جلسات ورموز التحقق والاستعادة.
3. `data_requests`, وتصدير `audit_logs` قبل تصفيره حسب سياسة الاحتفاظ.
4. `coupon_redemptions`, `payments`, `invoices`, `subscriptions`.
5. `expense_splits`, `trip_expenses`, `settlements`.
6. `journal_lines`, `journal_entries`, `circle_turns`, `circle_configs`.
7. `transactions`, `contribution_plans`, `documents`, `document_sequences`, `invites`.
8. `tenant_resources`, `payment_provider_settings`, `tenant_memberships`.
9. `members`, `spaces`, `customer_profiles`, `platform_roles`, `auth_credentials`.
10. `tenants`, ثم `users`.
11. حذف الكوبونات التجريبية وإعادة زرع الباقات الأساسية فقط.

يجب كتابة اختبار Integration لهذا السكربت يثبت أن القاعدة بعد التصفير تحتوي المخطط والهجرات والباقات فقط، وأن إنشاء أول مدير ينجح.

## 5. إنشاء حساب المدير

### تنفيذ سريع وآمن باستخدام الكود الحالي

1. اختيار بريد مالك لا يستخدمه أي حساب آخر.
2. وضع هذا البريد مؤقتاً في `WAZEN_ADMIN_EMAILS` داخل Vercel Production.
3. التأكد من تعطيل Demo والرؤوس الموثوقة وربط قاعدة الإنتاج الجديدة.
4. نشر الكود الحالي.
5. التسجيل من `/register` بهذا البريد، ثم تأكيد البريد.
6. يتحول الحساب إلى `super_admin` لأن البريد موجود في القائمة المصرح بها.
7. الدخول إلى `/account/security` وتفعيل TOTP فوراً.
8. التحقق من `/admin` ومن سجل التدقيق.
9. إزالة `WAZEN_ADMIN_EMAILS` من البيئة بعد نجاح التهيئة وإعادة النشر؛ الدور يبقى في قاعدة البيانات.
10. إنشاء مدير احتياطي مستقل، محمي بـTOTP، وتخزين رموز الاستعادة خارج النظام.

لا ينبغي إنشاء كلمة مرور المدير داخل SQL أو إرسالها في محادثة أو حفظها في متغير بيئة دائم.

### التنفيذ الأفضل طويل الأمد

إضافة جدول `admin_bootstrap_tokens` وسكربت `scripts/bootstrap-admin.mjs`:

- يقبل البريد فقط.
- ينشئ رمزاً عشوائياً، ويحفظ hash فقط، وصلاحيته 15 دقيقة واستخدامه مرة واحدة.
- يفتح رابط `/admin/setup?token=...` لتعيين الاسم وكلمة المرور وتفعيل TOTP في نفس الجلسة.
- لا يصبح الحساب `super_admin` إلا بعد تأكيد البريد وTOTP.
- يمنع خفض أو حذف آخر مدير أعلى.
- يسجل كل خطوة في سجل التدقيق دون حفظ الرمز أو كلمة المرور.

## 6. تصميم لوحة الإدارة المطلوبة

### المسارات

- `/admin/overview`: مؤشرات حقيقية مجمعة من الخادم.
- `/admin/users` و`/admin/users/[id]`: العملاء والحساب والجلسات والاستخدام.
- `/admin/tenants` و`/admin/tenants/[id]`: الشركات والمحافظ والأعضاء.
- `/admin/staff`: موظفو الإدارة والدعوات والأدوار.
- `/admin/subscriptions`: الاشتراكات والتجديد والإلغاء.
- `/admin/invoices` و`/admin/payments`: دورة الفوترة والتحصيل والاسترداد.
- `/admin/plans` و`/admin/coupons`: الباقات والأسعار والحدود والعروض.
- `/admin/documents`: بحث مركزي في المستندات دون كشف غير ضروري.
- `/admin/privacy-requests`: التصدير والحذف.
- `/admin/security`: الأحداث الأمنية والجلسات ومفاتيح API وتغييرات البوابات.
- `/admin/audit`: سجل تدقيق قابل للبحث والتصدير.
- `/admin/operations`: البريد وWebhooks والوظائف والهجرات وحالة النظام.
- `/admin/settings`: الدول والعملات والضرائب والبريد والدفع والإعدادات العامة.

### طبقة الخلفية

يجب عدم توسيع ملف `app/api/platform/route.ts` أكثر. يُقسم تدريجياً إلى:

- `services/admin/users-service.ts`
- `services/admin/billing-service.ts`
- `services/admin/tenants-service.ts`
- `services/admin/security-service.ts`
- `repositories/*` للاستعلامات والـpagination.
- Route handlers صغيرة تتحقق من المدخلات والصلاحيات وتستدعي الخدمات.

كل endpoint إداري يحتاج:

- صلاحية مركزية محددة.
- Pagination وحد أقصى للصفحة.
- فلترة وSort مسموحان فقط بقائمة بيضاء.
- CSRF وجلسة، مع منع API Key في إجراءات الإدارة الحساسة.
- سبب إلزامي للإجراءات الحساسة وAudit موحد.
- Step-up TOTP لتغيير الأدوار والبوابات والاسترداد والتصدير والحذف.

### مصفوفة أدوار مقترحة

| الدور | الصلاحيات الأساسية |
|---|---|
| `super_admin` | كامل النظام، الموظفون، الإعدادات والبوابات |
| `admin` | المستخدمون والباقات والتشغيل دون إدارة آخر super admin |
| `finance` | الفواتير والمدفوعات والتسويات والتقارير |
| `support` | قراءة الحسابات والمساعدة دون كشف أسرار أو تعديل مالي |
| `security_auditor` | قراءة أحداث الأمان والتدقيق دون تعديل |
| `content_manager` | النصوص والقوالب والإعلانات فقط |

## 7. تغييرات قاعدة البيانات المقترحة

- `admin_staff_invites`: دعوات موظفي الإدارة.
- `admin_bootstrap_tokens`: تهيئة المدير الأول بأمان.
- `security_events`: محاولات الدخول والأحداث الأمنية المنظمة.
- `admin_approvals`: الموافقات المزدوجة للإجراءات عالية الخطورة.
- `system_settings`: إعدادات غير سرية بإصدارات.
- `feature_flags`: الإطلاق التدريجي.
- `plan_prices`: أسعار بإصدارات ودول وعملات بدلاً من تعديل السعر التاريخي.
- `payment_attempts`: كل محاولة دفع واستجابة مزود منقحة.
- `refunds`: الاستردادات الجزئية والكاملة ككيانات مستقلة.
- `notification_preferences` و`notifications`.
- `support_cases` إذا لم نربط خدمة خارجية.

كما يلزم إضافة مفاتيح خارجية واضحة للجداول القديمة التي تعتمد حالياً على الانضباط البرمجي، وإنشاء migrations تدريجية مع اختبارات بيانات قبل فرض القيود.

## 8. مراحل التنفيذ والمدة التقديرية

### المرحلة 0 — إنقاذ النشر الحالي: 1–2 يوم عمل

- ربط GitHub/Vercel بالفرع الصحيح.
- تعطيل Demo، إضافة قاعدة Staging، نشر الكود الحالي وفحص API والأمان.

### المرحلة 1 — التصفير والمدير: 1–2 يوم

- Backup، قاعدة جديدة أو سكربت reset، هجرات، أول مدير، TOTP واختبارات قبول.

### المرحلة 2 — الإدارة الأساسية: 5–8 أيام

- المستخدمون التفصيليون، المستأجرون، فريق الإدارة، pagination، الصلاحيات وAudit.

### المرحلة 3 — التجارة والفوترة: 5–8 أيام

- الباقات بإصدارات، الاشتراكات، الفواتير، محاولات الدفع والاستردادات والكوبونات.

### المرحلة 4 — التشغيل والأمان: 4–6 أيام

- Security events، jobs، Webhooks، البريد، المراقبة، الموافقات وطلبات الخصوصية.

### المرحلة 5 — الجودة والإطلاق: 3–5 أيام

- E2E للأدوار، اختبار عزل متعدد المستأجرين، فحص وصول، حمل أساسي، استعادة Backup، وإطلاق محدود.

الإجمالي الواقعي للنسخة الإدارية التجارية: نحو 18–29 يوم عمل، باستثناء المراجعة القانونية وربط مزود دفع قد يستغرق موافقات خارجية.

## 9. معايير القبول قبل فتح الموقع

- الزائر غير المسجل لا يرى `/dashboard` أو `/admin` ولا أي بيانات تجريبية.
- `/api/health` يعمل، ونسخة التطبيق والمخطط معروفتان.
- قاعدة الإنتاج جديدة أو مصفرة مع تقرير قبل/بعد ونسخة قابلة للاستعادة.
- يوجد مديران حقيقيان على الأقل، وكلاهما بتأكيد بريد وTOTP.
- لا يستطيع الدعم تعديل الدفع، ولا المالية إدارة موظفي الإدارة.
- لا يستطيع أي مستأجر قراءة معرفات أو بيانات مستأجر آخر.
- كل تغيير دور أو دفع أو بوابة أو حذف/تصدير له Audit وسبب وممثل واضح.
- التقارير تحسب من استعلامات خادم مجمعة وليست رسوماً ثابتة أو كل البيانات في المتصفح.
- Webhook وidempotency والاسترداد والترقيم يجتازون اختبارات السباق.
- CI والبناء والتدقيق الأمني وE2E ناجحة.
- Backup واستعادة تجريبية ناجحان قبل تحويل الزيارات.

## 10. قرارات مطلوبة من المالك

قبل التنفيذ التدميري يلزم تحديد:

1. بريد واسم المدير الأساسي والمدير الاحتياطي، دون إرسال كلمات المرور.
2. هل البيانات الحالية كلها تجريبية ويمكن حذفها، أم توجد بيانات يجب أرشفتها؟
3. هل نستخدم قاعدة إنتاج جديدة — وهو الموصى به — أم نصفر نفس القاعدة؟
4. مدة الاحتفاظ بالنسخة القديمة وسجلات التدقيق والفواتير.
5. مزود الدفع والبريد والدول التي سيبدأ بها الإطلاق.
6. هل تبدأ المنصة بدعوات فقط أم تسجيل عام؟

## 11. ترتيب العمل المقترح فور الموافقة

1. إنشاء فرع `agent/production-reset-admin` ورفع الكود المؤمّن.
2. إنشاء Staging مطابق للإنتاج واختباره.
3. بناء سكربت reset آمن وbootstrap للمدير مع اختبارات.
4. إنشاء قاعدة إنتاج جديدة وتشغيل الهجرات.
5. إنشاء المدير وتفعيل TOTP.
6. نشر الإدارة الأساسية المحسنة.
7. اختبار قبول موثق ثم تحويل Vercel إلى قاعدة الإنتاج الجديدة.

لا ينبغي تنفيذ التصفير قبل الحصول على موافقة صريحة على البيئة والبيانات المراد حذفها ووجود نسخة احتياطية قابلة للاستعادة.
