## 1. المثال المرجعي الذي يشرح النظام

### 1.1 السيناريو (من مالك المنتج)

> أنشأتُ جمعية/محفظة سفر **بيني وبين إخوتي**.  
> **المساهمة الشهرية الإلزامية = 20 ريالاً** على كل شخص.  
> يمكن لأي شخص إرسال **أكثر من 20**.  
> المبلغ الفائض/الإضافي **لا يدخل ملكية حساب الجمعية**.  
> يظهر **مبلغاً إضافياً للشخص** حتى يريده أو عند السفر؛  
> أي أنه **فائض شخصي** محمي.

### 1.2 كيف يجب أن يسجّل النظام دفعة أحمد 50 ريالاً؟

| البند | المبلغ | المعنى المحاسبي/المنتجي |
|--------|--------|--------------------------|
| الاشتراك الإلزامي لهذا الشهر | **20 ر.س** | يدخل **الصندوق المشترك** (قابل للصرف الجماعي وفق القواعد) |
| الرصيد الشخصي الإضافي لأحمد | **30 ر.س** | **التزام على المحفظة لصالح أحمد**؛ ليس دخلاً للجمعية |
| النقد المستلم فعلياً لدى أمين الصندوق | **50 ر.س** | ما وُجد نقداً/في الحساب الحقيقي |

### 1.3 ثلاثة أرقام التي يجب عرضها دائماً

| الرقم | قيمة المثال بعد دفعة أحمد | الوصف |
|-------|---------------------------|--------|
| **رصيد الصندوق المشترك القابل للصرف** | 20 | ما يجوز صرفه لمصروف جماعي بعد القواعد |
| **رصيد أحمد الشخصي الإضافي** | 30 | ملك أحمد داخل عهدة المجموعة |
| **إجمالي الأموال الموجودة فعلياً** | 50 | مشترك + فوائض (+ مخصصات − ما صُرف فعلياً… انظر معادلة المصالحة) |

### 1.4 لماذا هذا الفصل ضروري؟

- **30 ريالاً ليست ربحاً ولا دخلاً للجمعية.**  
- هي **دين/عهدة** على الصندوق تجاه العضو.  
- خلطها مع المشترك يسبب خلافاً عند الصرف أو الإلغاء أو الانسحاب.  
- هذا القرار هو **نواة ميزة وازن** مقابل تطبيقات «مصاريف مشتركة» التقليدية.

### 1.5 كيف يدعمها الكود الحالي (جزئياً)

| المفهوم | في القاعدة / API |
|---------|------------------|
| المساهمة الإلزامية | `contribution_plans.amount_minor` + سياسة `extra_policy` الافتراضية `personal_reserve` |
| الفائض الشخصي | `members.extra_minor` |
| تصنيف الدفعة | `transactions.allocation` مثل `personal_reserve` / `mandatory` / `general` |
| عدم رفع رصيد الصندوق عند الفائض | في `POST /api/dashboard` action `addTransaction`: إذا `allocation === "personal_reserve"` → `balanceDelta = 0` ويزاد `extra_minor` |
| الصندوق المشترك | `spaces.balance_minor` |

**ما زال ناقصاً لهذه المثال بالكامل في UI/API:**

- تقسيم تلقائي لدفعة 50 → (20 إلزامي + 30 فائض) في خطوة واحدة.  
- اختيار صريح عند الدفع: فائض / مقدم / تطوع / مخصص / توزيع.  
- طلب استرداد الفائض + موافقة المدير + إثبات تحويل.  
- سياسات الاسترداد (فوري / موافقة / أيام محددة / قبل السفر / مجمّد).  
- عرض «ثلاثة أرقام» كـ KPI ثابت في كل شاشة محفظة.

## 2. الفكرة الكاملة المرتبة

### 2.1 جملة المنتج

**وازن** منصة لإدارة الأموال **الشخصية والمشتركة** للأفراد والعائلات والمجموعات:  
ليست محفظة واحدة، بل نظام يفصل بدقة بين:

1. **أموال المجموعة (الصندوق المشترك)**  
2. **التزامات الأعضاء (المطلوب / المدفوع / المتأخر)**  
3. **أموال كل عضو الشخصية الموجودة لدى المجموعة (الفائض / المقدم / المخصص)**  
4. **المال الشخصي الخاص خارج المجموعات (محفظة شخصية خاصة)**

### 2.2 أربعة (ثم أكثر) منتجات مترابطة فوق محرك واحد

| # | المنتج | الغرض |
|---|--------|--------|
| 1 | محافظ الادخار العائلية والسفر | هدف مشترك + مساهمات + فوائض |
| 2 | الجمعيات الدورية وتوزيع الأدوار | أقساط + أدوار + توزيع |
| 3 | الرحلات وتقسيم المصروفات والتعويضات | ميزانية + من دفع + تسوية |
| 4 | إدارة الدخل والمصروف الشخصي | ميزانيات + أهداف + تقارير |
| + | منزل / مناسبة / مشروع | قوالب على نفس المحرك |

### 2.3 وحدة الحساب

- حساب مستخدم واحد → مساحات مالية متعددة (Spaces).  
- كل مساحة: أعضاء + أدوار + قواعد + أرصدة منفصلة.  
- المحرك المالي واحد؛ **القواعد والواجهة تختلف حسب القالب**.

### 2.4 الهرمية المفاهيمية

```
حساب المستخدم
├── المحفظة الشخصية (خاصة بالكامل افتراضياً)
│   ├── حسابات: نقد / بنك / محفظة رقمية / بطاقة / ادخار / ديون
│   ├── دخل + مصروف + تصنيفات
│   ├── ميزانيات شهرية
│   └── أهداف ادخار
├── محفظة المنزل
│   ├── صندوق مشترك
│   ├── مساهمات إلزامية
│   ├── أرصدة شخصية للأعضاء
│   └── فواتير ومتكررات
├── محفظة السفر / ادخار جماعي
│   ├── اشتراكات إلزامية
│   ├── فوائض شخصية
│   ├── أهداف وميزانية بنود
│   └── مصروفات + تعويضات + تسوية
└── الجمعية الدورية
    ├── أقساط واستحقاقات
    ├── أدوار وترتيب المستفيدين
    ├── توزيعات
    └── فوائض (إن سُمح)
```

## 3. المحرك المالي الموحد

### 3.1 أنواع «الأرصدة/العهد» داخل أي مساحة مشتركة

| النوع | ملك من؟ | يُصرف جماعياً؟ |
|-------|---------|----------------|
| الصندوق المشترك | المجموعة | نعم (بقواعد) |
| الفائض الشخصي | العضو | لا، إلا بموافقته |
| دفعة مقدمة | تُحتسب لاحقاً لاشتراكاته | لا كصرف جماعي عام |
| مبلغ مخصص لهدف | حسب السياسة | لهدف محدد فقط |
| مستحق لعضو (سدّد من جيبه) | دين للمجموعة/الأعضاء نحوه | يُسوّى لاحقاً |

### 3.2 معادلة المصالحة المالية (للمدير)

```
الأموال الموجودة فعلياً
  = الصندوق المشترك
  + أرصدة الأعضاء الشخصية (فوائض/مخصصات…)
  + المبالغ المخصصة
  − ما دُفع فعلياً للموردين ولم يُطابق بعد (أو يُدار عبر بنود العهد)
```

**تنبيه منتجي:** إذا الرصيد المسجّل ≠ النقد/البنك الحقيقي → تنبيه «عدم تطابق» للمراجعة.

### 3.3 مبدأ القيد (مستهدف محاسبي)

التوجيه طويل الأمد: **دفتر قيود مزدوج (Double-entry)** غير قابل للحذف؛  
التصحيح = قيد عكسي.  
الوضع الحالي في الكود أقرب إلى: تحديث رصيد مباشر + سجل عملية (انظر قسم المصفوفة).

### 3.4 وحدات المبلغ

- التخزين بوحدة صغرى (`*_minor`) لتفادي أخطاء الفاصلة.  
- العرض بعملة المساحة (افتراضي SAR في النسخة الحالية).

## 4. محافظ الادخار والسفر

### 4.1 الإعداد

- إنشاء محفظة سفر/ادخار.  
- تحديد الاشتراك الإلزامي الدوري (مثال: 20 ر.س / شهر / عضو).  
- دعوة الأعضاء.  
- سياسة الزيادة الافتراضية: **رصيد شخصي قابل للاسترداد**.

### 4.2 أنواع الزيادة عند دفع أكثر من المطلوب

عند دفع زائد يسأل النظام (متطلب منتج):

| الخيار | الأثر |
|--------|--------|
| رصيد شخصي قابل للاسترداد | ملك العضو؛ لا يدخل الصندوق |
| دفعة مقدمة | تغطي أشهر قادمة |
| مساهمة تطوعية | تصبح ملك الصندوق المشترك |
| مبلغ مخصص لهدف | تذاكر / سكن / طعام / نشاط |
| توزيع المبلغ | جزء مقدم + جزء فائض + جزء تبرع… |

### 4.3 استخدام الرصيد الشخصي الإضافي

يقدر العضو على:

1. طلب استرداده.  
2. استخدامه لتغطية حصته عند السفر.  
3. تحويل جزء منه لمساهمة مشتركة بموافقته.  
4. تحويله إلى دفعات مقدمة.  
5. الاحتفاظ به لهدف معين.  
6. الاطلاع على كل حركاته.

**قاعدة صارمة:** لا يستخدمه المدير في مصروف جماعي إلا بموافقة العضو.

### 4.4 طلب استرداد الفائض (سير عمل)

1. يطلب العضو استرداد مبلغ (مثل 15).  
2. إشعار للمدير / أمين الصندوق.  
3. موافقة + تسجيل تحويل.  
4. إرفاق إثبات (اختياري/إلزامي حسب السياسة).  
5. ينخفض `extra` من 30 → 15.  
6. تُحفظ في سجل التدقيق.

### 4.5 سياسات الاسترداد (إعدادات المساحة)

| السياسة | الوصف |
|---------|--------|
| فوري دون موافقة | ضمن حدود |
| يحتاج موافقة المدير | **موصى به افتراضياً** |
| أيام محددة | نوافذ صرف |
| قبل السفر فقط | نافذة زمنية |
| مجمّد حتى موعد | قفل |

**توصية المنتج:** قابل للاسترداد + موافقة مدير + توثيق تحويل.

## 5. أهداف السفر والميزانية

### 5.1 بيانات الهدف

- الوجهة (مثال: إسطنبول).  
- التاريخ المتوقع (يوليو 2027).  
- الميزانية المطلوبة (12,000).  
- عدد المشاركين (6).  
- المساهمة الشهرية (20).  
- بنود متوقعة: طيران، سكن، مواصلات، طعام وأنشطة، طوارئ.

### 5.2 ما يعرضه النظام

- المجموع المحصّل من الصندوق (بدون خلط الفوائض).  
- نسبة الهدف.  
- المتبقي.  
- كفاية المساهمة الحالية حتى الموعد.  
- **مساهمة شهرية مقترحة** للوصول.  
- رصيد الصندوق vs مجموع الفوائض الشخصية **منفصلين**.

### 5.3 مثال التوقع (متطلب منتج قوي)

> بالمساهمة الحالية ستصلون إلى 8,400 فقط.  
> للوصول إلى 12,000 قبل الموعد يجب رفع مساهمة كل عضو إلى ~29 شهرياً.

## 6. المصروفات والتعويضات

### 6.1 مصروف من الصندوق المشترك

- مثال: 500 للفندق من حساب المجموعة.  
- ↓ الصندوق المشترك.  
- لا تمس الفوائض الشخصية.

### 6.2 مصروف دفعه عضو من جيبه

- مثال: أحمد دفع 600 تذاكر عن 6.  
خيارات المعالجة:

| المسار | النتيجة |
|--------|---------|
| A | لأحمد **مستحق 600** على صندوق الرحلة |
| B | توزيع 100 على كل عضو |
| C | مزيج: جزء من الصندوق + جزء من الأعضاء |

### 6.3 مصروف شخصي

- لا يُحمَّل على الجميع.  
- يمكن خصمه من فائضه الشخصي بعد موافقته.

## 7. الجمعيات الدورية

### 7.1 إعدادات الجمعية

- مساهمة دورية.  
- عدد الأعضاء.  
- مدة الجمعية.  
- مبلغ كل دور.  
- موعد الدفع.  
- قواعد التأخير والانسحاب.  
- طريقة ترتيب المستفيدين.

### 7.2 طرق ترتيب الأدوار (محرك مطلوب)

1. يدوي  
2. حسب الانضمام  
3. أبجدي  
4. قرعة إلكترونية موثقة  
5. متناوب  
6. هرمي / عكسي  
7. تصويت  
8. أولوية حسب الحاجة  
9. خوارزمية مخصصة بشروط المدير  

### 7.3 حساب العضو في الجمعية

- إجمالي المطلوب / المدفوع / المتبقي  
- متأخرات / مقدمات  
- المبلغ المستلم من الجمعية  
- موعد وترتيب دوره  
- رصيده الشخصي الإضافي إن سُمح  

> **ملاحظة:** السفر والجمعية منتجان مختلفان؛ يجمعهما المحرك (إلزامي vs فائض) لكن قواعد الأدوار والتوزيع خاصة بالجمعية.

## 8. أنواع قوالب المحافظ

عند «إنشاء محفظة» يختار المستخدم قالباً:

| القالب | الاستخدام |
|--------|-----------|
| ادخار جماعي | هدف مشترك |
| سفر | مساهمات + ميزانية + حجوزات + تسويات |
| جمعية دورية | أقساط + أدوار + توزيع |
| عائلية/منزل | فواتير + مساهمات أسرية |
| مناسبة | زواج / عزاء / عيد / تخرج |
| مشروع صغير | مساهمات شركاء + أرباح/مصروف |
| شخصية | دخل/مصروف/ميزانية/ديون/أهداف |

كل قالب = **نفس المحرك + واجهة وقواعد مختلفة**.

## 9. المحفظة الشخصية

### 9.1 الخصوصية

- خاصة بالكامل إلا بمشاركة صريحة من صاحبها.

### 9.2 الحسابات الداخلية (منفّذ في المحفظة الشخصية)

- نقد · بنوك · محافظ رقمية، برصيد افتتاحي يدخله المستخدم.
- الدخل والخصومات قواعد شهرية؛ **لا تُرحَّل تلقائياً** حتى يؤكد المستخدم (خصم / تجاهل / تعديل المبلغ).
- فاتورة ثابتة أو متغيرة (الكهرباء والماء والهاتف تتطلب مبلغ الشهر).
- أقساط بتاريخ بداية/نهاية وإجمالي يُقسَّم على أشهر؛ اللوحة تعرض المدفوع والمتبقي.

### 9.3 الدخل

- راتب، إضافي، مشاريع، إيجار، مكافآت، هدايا، استثمار…  
- متكرر / غير منتظم / متوقع / مستلم / متأخر.

### 9.4 المصروفات والتصنيفات

- سكن، طعام، مواصلات، تعليم، صحة، تسوق، اشتراكات، ترفيه، سفر، ديون، تحويلات عائلية، صدقات، مخصصات المستخدم.

## 10. المحفظة المنزلية والعائلية

صندوق عائلي مستقل: كل فرد يدفع مساهمة، والمصروف يُخصم من الصندوق نفسه. يُسجَّل رقم حساب الصندوق أو يُربط بحساب المدير/أمين السر. تذكير بطلعة/علاج بتاريخ ومبلغ متوقع؛ النظام يحسب المتوفر + الدخل المتوقع حتى التاريخ وينبّه عند العجز.

أدوار الجمعية الدورية **ليست** في المنزل ولا السفر ولا الشخصي — فقط نوع `society` / `group`.

### 10.1 أنواع الأموال داخل المنزل

- دخل عائلي مشترك  
- مساهمات أفراد  
- مصروفات مشتركة  
- مصروفات شخصية لعضو  
- رصيد شخصي محفوظ  
- مستحق لعضو دفع من ماله  
- مبالغ لأهداف عائلية  

### 10.2 نفس قاعدة الزيادة

دفع 700 ومطلوب 500 → 500 مشترك + 200 (فائض / مقدم / تطوع) حسب الاختيار.

### 10.3 مصروفات وتقسيم

- إيجار، فواتير، غذاء، عمالة، صيانة، تعليم، علاج، أقساط، مناسبات، طوارئ.  
- متكررات + تنبيه قبل الاستحقاق.  
- تقسيم: متساوٍ / بنسبة دخل / مخصص / أشخاص محددون / من الصندوق / من رصيد عضو بموافقته.

### 10.4 صلاحيات أسرية خاصة

- مالك · مدير عائلة · شريك مالي · عضو بالغ · ابن/تابع · مدقق.  
- «مصروف الأبناء»: أسبوعي/شهري، متبقي، أهداف، حدود، موافقة ولي أمر.

## 11. الخصوصية بين المحافظ

قواعد منتج إلزامية:

1. أفراد المجموعة **لا** يرون المحفظة الشخصية.  
2. الراتب **لا** يظهر إلا بإذن.  
3. يمكن مشاركة **إجمالي** بدون تفاصيل.  
4. يمكن مشاركة تصنيف فقط.  
5. مدير الجمعية لا يرى مصروفك الشخصي.  
6. صلاحيات محدودة للأبناء.  
7. تحويل 100 من شخصي → سفر = عمليتان مرتبطتان (خروج/دخول) **وليست دخذاً مزدوجاً** في التقرير الشامل.

### 21.2 ترتيب التنفيذ الموصى به *الآن* (متوافق مع فكرتك)

1. **إكمال «المثال المرجعي» من الألف للياء** (سفر/إخوة/20/فائض) بواجهة وAPI كاملين.  
2. **دفعة مركبة** + اختيارات الزيادة الخمسة.  
3. **استرداد فائض** + موافقة + تدقيق.  
4. **KPI الثلاثة أرقام** + معادلة مصالحة.  
5. **تقوية الأمان والحسابات** (قبل فتح عام).  
6. ثم: منزل أغنى → جمعية+قرعة → تسوية سفر → دفع مرخّص.

- قرار افتراضي واحد (مثال: الاسترداد دائماً يحتاج موافقة؟).

4. Contract tests لقاعدة: «الفائض لا يزيد balance المشترك».  
5. مصدر DB واحد دائم قبل التسويق (Neon/Turso/D1 إنتاج).

### 22.3 تجاري

1. الباقة المجانية: 1 محفظة مشتركة + 3 أعضاء.  
2. باقة العائلات: سفر+منزل.  
3. باقة الجمعيات: أدوار+قرعة.  
4. عدم بيع «تحويل أموال» حتى الترخيص.

### 22.4 تجربة المستخدم

1. معالج إنشاء: «إخوة سفر 20 شهرياً» بثلاث نقرات.  
2. لغة مالية بسيطة بجانب التقارير الاحترافية.  
3. وضع «أمين صندوق» مبسّط للجوال فقط.

## 23. قرار الامتثال المبدئي (أموال المستخدمين)

**معتمد من صياغة المنتج:**

> في البداية يسجّل النظام الأموال فقط؛

هذا القرار يجب أن يظهر في:

- واجهة المنتج (توضيح «لسنا بنكاً»)  
- الشروط والخصوصية  
- أولوية الميزات (لا نبني محفظة مرخصة قبل ledger وأمان)

**الخلاصة التنفيذية**
